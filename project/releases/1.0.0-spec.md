# Release spec — helps 1.0.0

Class: **change** (`process.project-lifecycle` R10): no new behaviour, but the public interface is
declared and the release process begins.

## 1. Context and scope

0.99.3 works and is used daily by the owner, but it was a release candidate: no tags, a version bump
per push, no declared interface, no project documents. The owner asked on 2026-11-21 for "a mature
product that others understand", checked against the UASK Engineering Hub. 1.0.0 builds on 0.99.3 and
the foundation of 2026-11-21.

## 2. Goals and non-goals

| ID | Requirement | Why in this release |
|---|---|---|
| NFR-12 | a released version never changes; earlier versions can be installed again | the core of "stable" |
| NFR-11 | MIT, English only | the directory and outside users |
| FR-1 – FR-19, FR-21, FR-22 | as built in 0.99.3 | carried over unchanged; now under the version promise |

Out of scope: FR-20 (directory listing) → after the owner's submission, AC-10; TD-2, TD-4 – TD-7 → 1.1.0.

Non-goals: any change of behaviour; new settings.

## 3. Design

No blueprint section changes in behaviour. The public interface is written down in
`docs/INTERFACE.md` 1.0.0 (blueprint §3, rows I-8, I-9, I-10). The release-candidate wording is removed
from the README and the manifests. No data migration.

## 4. Alternatives considered

- Release 0.99.4 and wait for the directory before 1.0.0 — rejected: the directory wants a stable
  version, and users of the marketplace need the version promise now.
- Change behaviour in the same release (TD-2, TD-7) — rejected: keeps 1.0.0 to the code that has run
  daily since 0.99.3.

## 5. Cross-cutting impact

Security, privacy, performance, accessibility, observability: none changed. Documented:
SECURITY.md (private reporting, 7 days).

## 6. Acceptance and verification

AC-1 – AC-8, AC-11 – AC-19 (gate and hand checks, recorded in `1.0.0.md` §2); AC-9 not tried by a
person (stated in the release notes); AC-10 after listing.

## 7. Rollout and rollback

After the owner's approval in `1.0.0.md`, the owner merges the pull request `release/1.0.0` → `main`;
the release workflow then tags the listed earlier versions and `v1.0.0` and builds the archives and
checksums from the merge commit. Agents push no tags. Rollback: RELEASING.md §Rollback; no data change,
so no backup is needed (the data folder is not touched by the update).

  switch answers. Not in our hands; watch, and say so in the README if it persists.
- Circuit breaker: at 2 agent-days the lead stops and asks the owner.
