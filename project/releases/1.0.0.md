## 3. Deploy plan

- Window: on approval.
- Who deploys: the lead · who can roll back: the lead, the owner.
- Steps:
  1. The branch `release/1.0.0` is on GitHub (pushed under SR-1). This session cannot push `main` or
     tags (GitHub refuses it, 403), so `main` changes only through a pull request the owner merges.
  2. After the owner's approval below: the owner opens the pull request `release/1.0.0` → `main` and
     merges it when the checks are green. On the merge the release workflow tags `v0.5.0` … `v0.99.3`
     from `releases/tags.txt` (the owner's yes, 2026-11-21), reruns the gate, builds the archives and
     checksums, tags `v1.0.0` and creates the GitHub release. The marketplace serves 1.0.0 from that
     moment.
  3. Users with auto-update get 1.0.0 at their next start; others with **Update now** and `/reload-plugins`.
- Expected duration: 15 minutes · Users informed: the update notice beside the lamp (FR-16), the
  GitHub release.

## 4. Backup (before deploy)

- What: nothing on users' machines changes; the data folder is not touched by an update.
- Where: the previous version stays installable from the tag `v0.99.3` (RELEASING.md §Rollback).

## 5. Rollback plan

- Triggers — roll back if, within a day of the release:
  - the band does not show in a new session where 0.99.3 showed it;
  - a session breaks or stops because of helps;
  - helps writes or sends anything the README does not list.
- Steps: for everyone, release 1.0.1 with the content of 0.99.3 plus the version bump; for one machine at
  once, install `v0.99.3` from its tag (RELEASING.md §Rollback).
- Expected time: 5 minutes per machine; 30 minutes for a 1.0.1. · Decides: the owner (the lead may roll
  back at once if a session breaks, and reports).
